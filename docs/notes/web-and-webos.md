# Web & webOS Technical Notes

Durable findings from web, PWA, TypeScript, Playwright, and Chrome 68 / webOS work. Add new notes only when they capture a non-obvious constraint future work must respect.

- Chromium 68's SwiftShader (2018, `OutputASM`) gives every temporary-qualified node its own register for the whole shader, never freed: named locals, parameters and every intermediate expression value, capped at 4096 (`sw::NUM_TEMPORARY_REGISTERS`). So branches don't help, only less code reachable from the entry point does. Chrome's ANGLE translator drops uncalled functions first, so what counts is the entry point's call graph (naga's GLSL still contains every function of the module). Overrides don't prune either: naga substitutes `FINE_PLANTS` but keeps both branches, and the coarse pipeline cost the same. The one-pass `fs_main` reached `plant_texel` (≈3400 registers alone) and `ground`; `fs_sprite` reaches `plant_texel` through `hidden_by_plant` and fits with under 10% to spare. Measured by padding the naga GLSL with a chain of N float statements (≈2 registers each) until it fails (the bare shader fails at ≈2040): the split passes use about 2300 (`fs_leaves`, `fs_stems`, `fs_sprite_stems`) and 2700 (`fs_ground`, `fs_sprite_leaves`), 30 to 45% headroom. `scripts/check-chrome68.ts` fails when a pass grows past the limit.
- By the algae coat (#178), `fs_ground` was down to about 136 padding statements of headroom, and the coat (`host_coat`, about 50), its water strands (`coat_fringe`, over 30), the rear glass film (about 35) and the in-layer front film (`front_over`, about 20) took it over. So `ground()` draws no algae: `ground_film` gives what lies over it, which `fs_main` blends in and the split grid draws in `fs_ground_film`, a pass drawn only while a coat or rear film shows (about 760 statements spare). The split grid always draws the front film in its own pass after the sprites. `fs_ground` keeps about 160 statements spare, the sprite passes about 250 to 280 and the plant passes about 470 to 500. Measure a pass by turning `tank.wgsl` into GLSL with naga (overrides applied) and compiling it, padded, in Chromium 68's WebGL2.
- The algae varieties (#369) initially computed slime (two value noises) and spots procedurally and read looks from an array in the view uniform. Chromium 68 compiled the split film passes but reported out of memory at their first draw (dynamically indexed `view.looks[id]` does that on its own, and inlined noise cost registers at every call site). Both grids now read the looks and the spot and slime patterns from a single baked atlas (`algae.rs`, 482×240, uploaded once): a texel fetch and a few operations per style. `fs_ground_film` keeps about 616 statements spare, `fs_front_film` 1113, and the other passes as before. For #393, dropping the duplicate `FINE_PLANTS` pipeline override eliminated the ~5.7 s lazy SwiftShader compile stall on the first scale change to 4×, and auto-enabling the split grid on software adapters (`Cpu` / `SwiftShader` / `llvmpipe`, paired with a non-sRGB surface so the split algae passes blend in encoded space) brought SwiftShader cold startup from ~6.5 s down to ~3.9 s while leaving `?grid=single` able to force one-pass for `check-chrome68.ts`.
- wgpu's WebGL2 surface presents an sRGB format with a shader pass whose vertex shader indexes a constant array by `gl_VertexID`; Chromium 68's SwiftShader draws nothing with that (a plain triangle written that way doesn't draw either), so even a valid frame left the canvas black. A non-sRGB format is presented with `blitFramebuffer`, which works there and saves a full-screen draw per frame. The shader already encodes for either (`srgb_target`), so the colours are the same. Chrome 68 on a real GPU (headless on the Mac, desktop GL) compiled the one-pass shader and presented sRGB fine: both limits are SwiftShader's, and whether the TV's Mali-G51 driver shares them is unconfirmed.
- Splitting `plant_texel` into separate functions moved one marimo texel at 320×180 by one ramp shade on Metal: its shade is `round(lit + 0.45)` with `lit` 4.05 there, a tie at 4.5 in exact arithmetic, so how the compiler contracts the float ops after inlining decides it. Shader refactors can flip such ties; the render tests' 0.5% tolerance absorbs them.
- Chrome 68 (webOS 5) can't compile a default Rust wasm32 module: sign-ext, bulk memory, saturating float-to-int, reference types (wasm-bindgen's externref table) and multivalue (which `wasm-opt --enable-multivalue -Oz` introduces) are all post-Chrome 68. `-C target-cpu=mvp` covers only our crates; the precompiled std still holds sign-ext, `memory.copy/fill` and `trunc_sat`, which binaryen lowers. wasm-opt enables whatever a module's `target_features` section lists on top of `--mvp-features`, so validating a module that still has that section proves nothing: the checker rejects the section first.
- esbuild lowers syntax to `chrome68` (keeping `import.meta`, which a plain `es2017` target would replace with `{}`); acorn has no "ES2018 + import.meta" mode, so the check parses at ES2020 and rejects the ES2019+ nodes Chrome 68 lacks. The ES2018 library in `web/tsconfig.webos.json` catches new built-ins (`replaceAll` was the only one), not DOM APIs: those were audited by hand (`replaceChildren`, `toggleAttribute`, `Blob.arrayBuffer`; `navigator.locks` is feature-detected, `inert` and CSS `gap` in flexbox, `min()`, `aspect-ratio` and `:focus-visible` degrade cosmetically).
- Chromium 68.0.3440.0 (snapshot 561733, `chrome-mac.zip`, x86_64 under Rosetta) runs headless on macOS 27 and can be driven over raw CDP (`--remote-debugging-port`); headed it crashes at start (`mach_port_broker: Permission denied`), and headless has no desktop GL, only its 2018 SwiftShader. There the webOS build starts with no error, every step in under 2.3 s (wasm 0.7 s, graphics `webgl2, Google SwiftShader`), rAF fires at 60 Hz and the sim ticks, so the TV's zero-frame start did **not** reproduce off-device with a visible page. But that SwiftShader rejects the `tank` and `tank (coarse plants)` fragment shaders ("Too many temporary registers required"), so the canvas stays black: a risk for the TV's Mali-G51 driver too, to check on the device.
- The webOS spike's zero rAF callbacks over 25 s fit a page launched with `visible:false` (`document.hidden`): rAF doesn't run in a hidden page and DeskTank's pause-when-hidden keeps its timers stopped too. The new diagnostics show this case as "hidden: waiting for the page to be shown" (with `?debug=1`).
- TypeScript: TypeScript 7's emitter re-indents with four spaces and drops blank lines, so the emitted page is a little larger raw (`main.js` 47 KiB against 44; 14.5 KiB gzip against 13.9); comments and statement order are kept, so it still reads like the source. Node's type stripping needs `erasableSyntaxOnly` (no enums, namespaces or parameter properties), `verbatimModuleSyntax` (`import type`) and `.ts` extensions on relative imports; `rewriteRelativeImportExtensions` lets `tsc` accept those and turn them into `.js` for the browser. Code inside `page.evaluate` is typed against the page (DOM lib, `window.desktank` from `web/hooks.d.ts`) but runs as the transpiled JS Playwright sends.
- TypeScript everywhere outside Rust: the web page (`web/main.ts`, `store.ts`, `ownership.ts`), the build, serve and bench scripts (`scripts/*.ts`), the Playwright tests and config were JavaScript (`.js`/`.mjs`) and are now strict TypeScript (TypeScript 7.0.2 and `@types/node` pinned as dev dependencies). Node runs the scripts by its built-in type stripping (`engines` now `>=22.18`; CI uses Node 24), so there is no loader; Playwright loads the `.ts` tests and config itself. `scripts/build-web.ts` runs wasm-bindgen with its TypeScript declarations into `target/web-bindgen/pkg/`, ships only the glue and wasm, and emits the page with `tsc -p web/tsconfig.json` (types stripped, comments kept, `.ts` imports rewritten to `.js`, source maps with inline sources; a type error fails the build). The page is checked against wasm-bindgen's `.d.ts` through `rootDirs`; `web/hooks.d.ts` types `window.desktank` for the page and the tests (`callTank` and `boxOf` in `tests/web/support.ts`). `pnpm typecheck` checks the Node side and the page (two programs, so the page never sees Node's `setTimeout`); CI's web job runs it after the build. Source maps are listed but not counted in the transfer size (only developer tools fetch them): 1477 KiB gzip, the page's JS 0.6 KiB of it more than before. AGENTS.md records the convention.
- wasm-bindgen's generated `unsafe` doesn't trip the workspace `unsafe_code = "deny"` lint (it comes from an external proc macro), so `desktank-web` needs no allow; CI runs clippy for `wasm32` to catch a change.
- The release profile's `strip = true` removes the `target_features` section wasm-bindgen reads, so the web build overrides it with `strip = "debuginfo"`. Demo wasm: 280 KiB, 218 KiB after `wasm-opt -Oz`.
- In the demo (Apple Silicon, Chrome, release wasm) a 320×180 pour ticks in about 1.5 ms; settled ticks about 0.1 ms.
- WB1 numbers (M3 Max, 120 Hz display, DPR 2, 1884×1060 canvas, 376×212 cells, 60 s of pouring): Chrome 157 (WebGPU) rAF interval p50 8.3 ms / p95 9.1 ms / max 49.6 ms, drawn frames p50 50.0 / p95 50.7 ms; Playwright WebKit 27.2 (WebGPU) rAF p50 17.0 / p95 18.0 / max 58 ms, drawn p95 51 ms. Playwright's Firefox wouldn't launch in the agent sandbox, so Firefox and real Safari are unmeasured.
- Transfer size: 1.07 MB gzip with `wasm-opt` locally, 1.17 MB in CI without it (wasm 2.7 MB / 3.8 MB raw: wgpu-core, naga's GLSL backend for WebGL2, and the sim).
- The renderer used to shade (water depth dim) in linear space on sRGB targets and in encoded space on `Rgba8Unorm` captures, so a window or WebGL2 canvas didn't match `desktank capture` (49% of pixels over ΔE 2). It now shades in encoded space everywhere and encodes for sRGB targets in the shader; the water in the native window is a little lighter at depth than before.
- A canvas keeps the first context type it hands out, so the WebGPU attempt opens the adapter and device before creating the surface, leaving the canvas free for the WebGL2 fallback. wgpu's default uncaptured-error handler panics (aborting the wasm module); the web host logs instead.
- Headless Chromium under DPR emulation reports CSS pixels in `devicePixelContentBoxSize`; the page sizes the canvas from the content box × `devicePixelRatio` instead.
- Headless Chromium on the Linux runner draws WebGL2 on SwiftShader only with `--enable-unsafe-swiftshader`; it matches the Metal reference to max ΔE 0.78.
- WB2 numbers (M3 Max, Chrome 157 WebGPU, DPR 2, 376×212 cells, on battery): settled and running, the page loop runs 20 times a second (one per tick; it was one per vsync, 60–120/s); a first timer version that re-entered through rAF ran 38/s, because the vsync timestamp often fell just before the tick was due. `pnpm bench:web chrome 30` with the cap at 30: loop interval p50 8.4 / p95 33.3 ms, drawn frames p50 41.1 / p95 47.7 ms; at the default auto cap on battery a frame the cap holds back now sleeps on the timer too (review fix): over 15 s of pouring the loop ran 51 times a second (was 106, spinning on vsync until the cap allowed a frame) and drawn frames were p50 68.9 / p95 70.3 ms (was 75 ms, rounded up to a vsync). Transfer size 1.15 MB gzip (was 1.14).
- rAF is only for vsync alignment, never a gate on ticks: a compositor can hold an animation frame back for most of a second (SwiftShader on a loaded 4-core runner running two Playwright workers doubled every web test's duration). The page keeps the tick timer armed while an rAF is pending. Settled and running it still wakes 20 times a second through the timer, with no rAF.
- On the GPU-less CI runner every drawn frame costs the renderer 90–140 ms of main-thread time on SwiftShader outside the page's JS (`tank.frame` itself took 1–15 ms; no `longtask` entries), and up to 400 ms while the other Playwright worker draws too, so the tick timer fires that late. The pacer then runs `MAX_CATCH_UP` (4) ticks and drops the rest by design, so a wall second held 5–13 ticks with two workers and 18 alone (diagnostics from PR CI runs). Tests must not assert ticks per wall second: bound ticks by the page's `performance.now()` and wait for progress with `expect.poll`. Real-time budgets (the steal between 1 and 2 s) need an uncontended runner, hence one CI worker. A user without a GPU sees the same slow-down; see Next increments.
- Headless Chromium reports the Battery Status API as discharging, so pages under Playwright run at the 15 fps battery cap unless the frame-cap setting fixes it.
- Playwright's touchscreen only taps; multi-touch drags go through CDP `Input.dispatchTouchEvent`, which Chromium turns into pointer events (and, with `isMobile`, real page scrolling, which the pinch/scroll test uses as its control).
- A stale `serve-web` from another worktree held port 8124, so `pnpm bench:web` silently loaded an old site and timed out; check `lsof -i :8124` if the bench never gets ready.
- WB4: Cache Storage is shared across Pages projects on the same origin. The build hashes the worker and shipped assets, including the Wasm module. Each worker installs its complete cache before activation and deletes older DeskTank caches for its own scope. Playwright runs the web suite under the Pages project path and checks the installed worker, cache cleanup and offline reload.
- WB3: the wasm build's save of a seeded scripted scene is byte-identical to the native one (the `layers` scene, 160 ticks with fields), so a web export is exactly what native writes. Web build 1.36 MB gzip with the save code linked (lz4, postcard, crc32).
- WB3: Web Locks give ownership for free: a queued `navigator.locks.request` turns a viewer into the owner when the owner's tab closes, `steal: true` covers a frozen owner, and the stolen owner learns of it from its request's `AbortError`. A handing-over owner must stop ticking before it saves, or the next owner opens an older state than the one the old owner shows.
- WB3: Playwright can't hide a headless Chromium tab; the tests override `document.hidden` / `visibilityState` and dispatch `visibilitychange`, which is what `main.ts` reads.
- WB3: a save carries the build's material and species name tables, so re-saving an older save isn't byte-identical once ids are added (T6c's runner and the new species changed them). The web tests compare an export against what native re-saves now (`crates/desktank-web/tests/fixtures/v1-resaved.dtank`, re-blessed with `DESKTANK_BLESS=1` like `layers-seed1.dtank`), not against the v1 file.
