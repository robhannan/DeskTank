# Android Technical Notes

Durable findings from Android TV / Google TV / emulator spikes and tests (A0–A2). Add new notes only when they capture a non-obvious constraint future work must respect.

- Tapsmith on the Dream (A2, 0.8.0): its UIAutomator2 agent installs and connects on Android TV (the SHIELD, API 30; the API 36 TV emulator in CI), and `takeScreenshot()` captures the Dream (a full-resolution 3840×2160 PNG on the SHIELD, RGBA). It has no adb-shell API, so the test runs `adb shell` itself (settings, `service call dreams`, `dumpsys dreams`, logcat); nor a getter for the selected serial, so the config passes `ANDROID_SERIAL` to Tapsmith as `device` and adb reads the same variable. Setting `package` makes Tapsmith clear and launch the app at suite startup even with `appReset: "none"`. The smoke test config omits it so each test can launch its own host. The Activity test clears the tank save before launch, and the Dream uses the shared save if present. Network capture is on by default (a device proxy) and telemetry is opt-out: both off in the config. `dumpsys dreams` prints the component in full (`io.github.robhannan.desktank/io.github.robhannan.desktank.DeskTankDream`). The Dream window fades in over the previous screen (about a second on the SHIELD), so the first screenshot mixes both; the test polls until the frame settles.
- A2 in CI: `reactivecircus/android-emulator-runner` once failed right after boot on its own `input keyevent 82` (adb exit 255) before the test ran; a re-run passed. On a panic the release build aborts, and libc's `Fatal signal 6` line names the process truncated (`hannan.desktank`), so the matcher keys on the tombstone's `>>> io.github.robhannan.desktank <<<` and the host's `panic:` line. The emulator logs `surfaceDestroyed: the render thread didn't release the surface in time` when the Dream ends (A1's 2 s wait on SwiftShader); it isn't a crash, so the test ignores it.
- A1 part 1 on real devices (2026-11-20, a local debug build of this PR over ADB; settings restored afterwards):
  - Both devices draw the tank at 4× on their 1920×1080 surface (480×270 cells, Vulkan, `Rgba8UnormSrgb`); screenshots on `pr-assets/android-render-tank/`. A remote key ends the Dream at once, the process then uses 0 CPU ticks over 30 s, and a second Dream in the same process continues the same tank with its first frame 38 ms after `surfaceCreated` (6 ms draw).
  - A cold start is slow: the first draw takes 6.6–6.7 s on the SHIELD (7.0–7.1 s after `surfaceCreated`) and 8.1 s on the Chromecast (8.7 s), against §6.1's 1 s. With debug logging the SHIELD shows two silent gaps of 3.2 s and 1.8 s right after naga parses `tank.wgsl`: the drivers compiling the two grid pipelines (`FINE_PLANTS` on and off) with no pipeline cache across processes. Device creation itself is 130–550 ms and the new world 30–150 ms.
  - Chromecast while dreaming: TOTAL PSS 112–118 MB (Native Heap 62 MB, Graphics 15 MB) against the 120 MB budget, and about 12% of one core (`/proc/<pid>/stat` over 30 s), roughly 7% on `desktank-render` and most of the rest in the Mali driver's threads.
  - The SHIELD's forced-GLES failure (A0, "Parent device is lost") now has a cause: its EGL gives wgpu a desktop OpenGL context (`Version: 3.3.0 NVIDIA 495.00`, `SL version: 3.30 NVIDIA via Cg compiler`), not GLES, and wgpu-core's indirect-draw validation then fails to build its compute pipeline (`indirect-validation error: ComputePipeline(Internal("The selected version doesn't support Features(BUFFER_STORAGE | COMPUTE_SHADER | DYNAMIC_ARRAY_SIZE)"))`), which `request_device` reports as a lost device. EGL also says it "can present to the window but not natively".
  - With `debug.desktank.log debug`, naga's shader-parse tracing floods logcat (thousands of lines per pipeline) and logcat drops lines; keep the default (wgpu warnings) except when chasing a device problem.
  - The A0 APK on the devices came from CI and is signed with CI's debug key, so a locally built APK needs `adb uninstall` first (`INSTALL_FAILED_UPDATE_INCOMPATIBLE`). Asking an asleep Chromecast to dream wakes the TV over HDMI-CEC, which wakes the Chromecast out of the Dream again; start it once the TV is on.
- A0 owner check on real devices (2026-11-20, debug APK from CI run 44749668974, commit 8e54f2b):
  - Chromecast with Google TV 4K (`ro.product.model=Chromecast`, device `sabrina`, `google/sabrina_prod_stable/sabrina:14/UTTC.250917.004/14193937:user/release-keys`, Android 14, API 34): a 32-bit-only userspace (`ro.product.cpu.abilist=armeabi-v7a,armeabi`, `abilist64` empty, `ro.zygote=zygote32`); the app installs with `primaryCpuAbi=armeabi-v7a` and the armeabi-v7a library works, so armeabi-v7a must stay in every build. 2 GB RAM (MemTotal 1982996 kB), Mali-G31 with Vulkan 1.3 (`feature:android.hardware.vulkan.version=4206592`) and GLES 3.2, a 3840×2160 panel with a `wm size` override of 1920×1080 (the UI runs at 1080p).
  - Its backend is Vulkan, despite the 32-bit userspace (no Vulkan guarantee there): `adapter: backend=Vulkan name="Mali-G31" type=IntegratedGpu driver="Mali-G31" driver_info="v1.r47p0-01eac0.d11afc3fbb435b14fc71a93974557794"`; `first frame 1920x1080 Rgba8UnormSrgb 211 ms after surfaceCreated` (208 ms on a later cold start, 39 ms on one start after a reboot). `screencap`: every pixel exactly `#1f4e79`. TOTAL PSS while dreaming 48,464 KB (Graphics 5,288 KB, Native Heap 9,580 KB), 38,977 KB on a later run.
  - Forced GLES on the Chromecast (`setprop debug.desktank.backend gl`, then `am force-stop`) works: `backend=Gl name="Mali-G31" driver_info="OpenGL ES 3.2 v1.r47p0-…"`, first frame 257 ms, `Rgba8UnormSrgb`, exactly `#1f4e79`, so the emulator's 565 EGL config doesn't show up here. TOTAL PSS 54,634 KB (Graphics 11,052 KB).
  - NVIDIA SHIELD Android TV 2019 Pro (`SHIELD Android TV`, device `mdarcy`, `NVIDIA/mdarcy/mdarcy:11/RQ1A.210105.003/7825230_3167.5736:user/release-keys`, Android 11, API 30; plain Android TV with `com.google.android.tvlauncher`): 64-bit with 32-bit support (`arm64-v8a,armeabi-v7a,armeabi`, `zygote64_32`), the app runs as arm64-v8a; 3 GB RAM, Vulkan 1.1, a 3840×2160 panel overridden to 1920×1080. Vulkan by default (`name="NVIDIA Tegra X1 (rev B) (nvgpu)" driver="NVIDIA" driver_info="495.00"`), first frame 1920×1080 `Rgba8UnormSrgb` 442 ms after `surfaceCreated` cold, 248–347 ms on later cold starts, 16 ms when a later Dream reuses the kept device; exactly `#1f4e79`. TOTAL PSS while dreaming 84,965 KB (Graphics/EGL mtrack 10,304 KB, Other mtrack 13,188 KB, Native Heap 22,128 KB), 83,155 KB with Vulkan forced, 72,108 KB after a reboot.
  - Forced GLES fails on the SHIELD: `no GPU surface: no backend worked: ["Backends(GL): could not open the GPU device: Parent device is lost"]`, and the screen stays black. wgpu-core's `request_device` returns `DeviceError::Lost`; the cause is unknown because wgpu's `log` output isn't routed to logcat. The default order picks Vulkan, so the Dream works, but there is no working fallback on this device yet (Next increments).
  - Both devices, as found (with their 1920×1080 `wm size` overrides), hand the Dream a 1920×1080 surface (the UI resolution, not the 4K panel), so A1 sizes the grid and scale from the surface. Whether `wm size reset` gives a 4K surface wasn't tried.
  - On both, a remote key (DPAD_CENTER) ends the Dream at once (`Stopping dream … reason='finished self'`); when not dreaming `top` shows 0.0–0.1% CPU and no DeskTank wake locks are held (the cached process is about 119 MB RSS on the Chromecast, 142 MB on the SHIELD). With a 30 s screensaver timeout set for the test the system starts the Dream itself (`Starting dream … reason='power manager request'`), also after a reboot, and `settings get secure screensaver_components` survives the reboot.
  - Google TV has no screensaver picker at all: `am start -a android.settings.DREAM_SETTINGS` gives "unable to resolve Intent". DeskTank can only be chosen with `adb shell settings put secure screensaver_components io.github.robhannan.desktank/.DeskTankDream` (or, untested, by an app granted `WRITE_SECURE_SETTINGS` over ADB once). Google's default is `com.google.android.apps.tv.dreamx/.service.Backdrop`, with a `screen_off_timeout` of 600000.
  - ADB over the network: the Chromecast refuses port 5555 and needs Android 11+ Wireless debugging (pair with a code via `adb pair`, then connect to the `_adb-tls-connect` port from `adb mdns services`; the port changes, and Wireless debugging turns itself off on reboot). The SHIELD takes legacy network ADB on 5555 after an on-screen authorisation.
  - With the "Stay awake" developer option on (`stay_on_while_plugged_in=3`, `mStayOn=true`) the screensaver timeout never fires, which the setup notes should say.
- A0 spike (evidence: CI spike run https://github.com/robhannan/DeskTank/actions/runs/44738214821, artifacts `spike-android-tv` and `spike-google-tv`, on the API 36 Android TV and Google TV x86_64 emulator images, `profile: tv_1080p`, `-gpu swiftshader_indirect`; screenshots on `pr-assets/android-skeleton/`):
  - Backend on the emulator: Vulkan by default (`SwiftShader Device (Subzero)`, type Cpu), drawing `#1f4e79` exactly into an `Rgba8UnormSrgb` surface; forcing GLES works (`OpenGL ES 3.0 SwiftShader`, `Rgba8Unorm`). First frame 100–330 ms after `surfaceCreated` on a cold process (device creation included), 10–120 ms for a later Dream in the same process (device kept).
  - GLES renders through a 16-bit EGL config: the water shows as `#214d7b`, exactly `#1f4e79` quantised to RGB565. wgpu-hal 30's `choose_config` asks for no colour sizes unless it uses sRGB, and the emulator's EGL has no sRGB, so the first config is 565; setting the `SurfaceView` holder to `RGBA_8888` made no difference (tried and reverted). Real devices may order configs differently; see Next increments.
  - wgpu 30 needs a display handle for any surface: without `InstanceDescriptor::display` both backends fail with "No `DisplayHandle` is available"; the host passes `DisplayHandle::android()`.
  - Starting a Dream from the command line (for A2) works as the plain shell user: `adb shell settings put secure screensaver_components io.github.robhannan.desktank/.DeskTankDream`, then `adb shell service call dreams 1` (`IDreamManager.dream()`) starts it and `service call dreams 2` (`awaken()`) ends it; `dumpsys dreams` shows `mCurrentDream`. `cmd dreams start-dreaming` needs root ("Must be root to call Dream shell commands", https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/core/java/com/android/server/dreams/DreamShellCommand.java) and these images are user builds (`adb root` is refused). SystemUI's `Somnambulator` no longer starts a Dream (https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/packages/SystemUI/src/com/android/systemui/Somnambulator.java). A 15 s `screen_off_timeout` with `screensaver_activate_on_sleep` did not start it within 30 s. The emulator runner's default AVD (no profile) gives a 320×640 display whose screenshots are black; use a TV profile.
  - Selecting a third-party Dream over ADB works on the Google TV emulator image (Android 16, `sdk_google_atv64_amati`): the same `settings put` plus `service call dreams 1` ran it. Google TV removed third-party screensavers from its picker in 2022 (https://github.com/theothernt/AerialViews, https://www.reviewgeek.com/125089/chromecast-with-google-tv-loses-third-party-screensavers/); no report found of the ADB setting being blocked since, but a 2025 update did block a launcher override (https://www.androidauthority.com/google-tv-update-blocks-projectivy-override-3649445).
  - Memory: an empty Dream's `dumpsys meminfo` TOTAL PSS is 42–47 MB on the emulator (Vulkan or GLES; Native Heap about 13 MB, Code 5–7 MB, Java Heap 9 MB, Graphics 0 since SwiftShader renders on the CPU), against the 120 MB budget (SPEC §6.1). A real GPU adds driver and graphics memory, so the device number is the one that counts.
  - 32-bit userspace: Chromecast with Google TV, Google TV Streamer, onn 4K boxes and most Fire TVs run a 32-bit userspace on 64-bit CPUs; only the Shield is 64-bit (https://www.aftvnews.com/?p=43549). Google Play requires arm64 alongside armeabi-v7a for TV apps from August 2026 (https://android-developers.googleblog.com/2025/08/64-bit-app-compatibility-for-google-tv-android-tv.html). wgpu and the crate build for `armeabi-v7a` (2.6 MB `.so`, against 3.7 MB arm64 and 4.2 MB x86_64; the debug APK with all three is 11 MB).
  - Vulkan: Android requires Vulkan 1.1 only of 64-bit, non-low-RAM devices (https://source.android.com/docs/core/graphics/implement-vulkan), and the TV CDD adds nothing (https://source.android.com/docs/compatibility/16/android-16-cdd), so the 32-bit Google TV devices above have no Vulkan guarantee: expect GLES there (the owner check found Vulkan on the 32-bit Chromecast anyway, above).
  - `minSdk` 26 (Android 8): every Google TV device launched on Android 10 or later, NDK r30 supports API 21 and up, and no target device needs lower. `cargo ndk --platform 26` links against the same level.
  - 16 KB pages: with NDK r30 the arm64 and x86_64 libraries come out 16 KB aligned (`LOAD … 0x4000`), as Android 15+ 16 KB devices and Play need (https://developer.android.com/guide/practices/page-sizes); armeabi-v7a is 4 KB, which the rule doesn't cover.
